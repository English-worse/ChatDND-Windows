# Windows 应用级免打扰工具设计规格

- 日期：2026-09-23
- 状态：已确认，进入实施计划
- 暂定产品名：ChatDND
- 目标平台：Windows 10/11 x64
- 目标形态：常驻托盘的独立桌面程序
- 内存目标：空闲工作集尽量低于 80 MB，发布前记录实际测量值
- 界面语言：简体中文为主，必要的英文术语保留并附中文说明
- 权限模式：默认普通用户权限；管理员模式由用户主动选择并确认风险
- 启动行为：完成首次配置后，默认打开程序立即开启免打扰；首次运行先完成应用选择

## 1. 背景

Windows 11 的勿扰模式主要抑制系统通知和 Shell 通知，不拦截微信、QQ、钉钉等桌面应用自行播放的提示音。用户需要的是应用级免打扰：

- 手动开启或关闭免打扰。
- 完成首次配置后，打开程序默认立即开启免打扰；用户可在设置中改为只打开主界面。
- 免打扰开启时，选中聊天应用的全部音频会话静音。
- 同时覆盖已经打开的应用和后来打开的多开实例。
- 不影响音乐、视频、浏览器等未选中的应用。
- 关闭免打扰后，只恢复本工具修改过的会话，不覆盖用户原本的静音状态。

本设计采用方案 A：静音选中聊天应用的全部音频。语音和视频通话也属于该应用的音频会话，因此会被静音。

## 2. 约束与非目标

### 2.1 低内存占用

- 不使用 Electron、WebView、内嵌浏览器或大型 UI 框架。
- 使用单个后台扫描循环，避免为每个音频会话创建独立线程。
- Core Audio 对象和进程信息使用后及时释放，避免长期持有 COM 对象。
- 日志采用滚动文件，避免无限增长。
- 空闲时目标工作集尽量低于 80 MB；它作为优化目标，不等于以牺牲稳定性为代价的硬门槛。
- 发布前必须记录空闲、静音运行和长时间运行三种场景的内存数据。

### 2.2 不修改应用内部

ChatDND 只能修改 Windows 音频会话的 Mute 状态，不得修改微信、QQ、钉钉或其他应用的内部状态。

明确禁止：

- 不读取或修改联系人、通讯录、聊天记录、好友状态、群设置或免打扰设置。
- 不调用微信、QQ、钉钉的私有 API，不模拟操作其界面。
- 不写入目标应用的安装目录、配置目录、注册表或账号数据。
- 不注入目标进程，不安装驱动，不劫持网络请求。
- 不读取消息内容、窗口文本、剪贴板、键盘输入或麦克风内容。

程序对目标应用产生的影响只能来自 Windows Core Audio 的会话静音和恢复。

### 2.3 中文界面

- 主窗口、托盘菜单、设置页、按钮、提示框、错误信息和状态文本全部使用简体中文。
- 必要的英文技术名词可以保留，但必须提供中文说明，例如显示为“进程 ID（Process ID）”或“音频会话（Audio Session）”。
- 面向用户的对话框不直接显示英文异常堆栈，详细英文错误只写入日志。
- 代码标识符、第三方库名称和 Windows API 名称可以保留英文。

### 2.4 管理员模式

- 默认以当前用户普通权限运行，不静默提权，不在启动时自动弹出 UAC。
- 用户可以在界面中选择“以管理员身份运行”，用于尝试处理权限更高的音频会话。
- 选择管理员模式前必须显示中文风险说明；用户取消 UAC 或拒绝风险说明时，程序继续以普通模式运行或正常退出。
- 管理员模式只提升进程权限，不改变程序边界：仍然只操作 Windows Core Audio 音频会话，不修改目标应用内部。
- 普通模式已经可以静音大多数聊天软件；管理员模式是兼容性选项，不是必需条件。

管理员模式的风险提示必须包含以下内容：

1. 管理员权限会扩大程序的影响范围。如果程序本身存在漏洞，或者程序文件被替换，潜在影响可能从音频控制扩大到系统级操作。
2. Windows 会弹出 UAC 确认窗口。用户必须理解并同意后，系统才会授予管理员权限。
3. 如果为了绕过 UAC 而使用任务计划程序自动以最高权限启动，会降低系统的安全边界，因此必须由用户单独开启。
4. 管理员权限不能保证控制所有受保护、独占模式或跨会话的音频会话。
5. 管理员模式不会改变隐私边界。程序仍然不访问联系人、聊天记录、应用配置或账号状态，也只修改音频会话的静音状态。

### 2.5 非目标

- 不做微信小程序、手机端应用或浏览器插件。
- 不做音频驱动、APO、DLL 注入或内核级音频拦截。
- 不保证在应用创建音频会话之前拦截第一声极短提示音。
- 不在第一版中区分消息提示音、语音通话和视频声音。
- 不读取聊天消息，不访问网络，不上传任何数据。

## 3. 现有项目检索结论

GitHub 上存在可复用的音频会话控制参考，但没有找到完全满足本规格的现成程序。

| 项目 | 相关能力 | 与本需求的差距 | 结论 |
|---|---|---|---|
| nefares/Background-Muter | 按前台/后台状态自动静音应用，托盘运行，.NET 8 | 不是手动免打扰；前台应用保持有声；许可证为 GPL-3.0 | 只作架构和交互参考，不直接复制代码 |
| YetSen-26/AutoMute | 自动静音后台进程，白名单，Core Audio 会话控制 | 行为是后台自动静音，不是全局免打扰；项目较新 | 可参考匹配和恢复思路 |
| simon-hirst/AudioMuter | 单个音频会话按需静音，支持定时恢复 | 一次只绑定一个会话，不覆盖多应用和多开 | 可参考托盘和定时恢复交互 |
| IxYusi/Per-app-audio-mixer | pycaw 实现每应用音量和静音，网页控制 | 手动控制，没有免打扰状态机和新会话自动覆盖 | 只作技术验证参考 |
| File-New-Project/EarTrumpet | 成熟的 Windows 音量控制实现 | 是手动音量混合器，不是免打扰工具 | 可参考 Core Audio 使用方式 |
| arda-ceylan/SonarCord | WASAPI 音频会话静音 | 仅针对特定声卡和 Discord 回声场景 | 不适用 |
| tpt-solutions/tpt-focus | 号称统一通知和专注中心 | 缺少可验证文档和成熟度 | 不作为依赖 |

结论：独立实现 ChatDND，不引入驱动，不复制 GPL 代码。

## 4. 技术方案

### 4.1 核心机制

使用 Windows Core Audio/WASAPI：

1. 枚举所有活动播放设备。
2. 枚举设备上的音频会话。
3. 通过会话获取进程 ID。
4. 将进程 ID 解析为规范化进程路径。
5. 用应用规则匹配进程路径。
6. 通过 `ISimpleAudioVolume` 设置或恢复静音状态。

静音操作只改变 Mute 状态，不修改用户的音量大小。

### 4.2 技术栈

- 语言：C#。
- 运行时：.NET 10 Windows。
- UI：Windows Forms，使用 `NotifyIcon` 实现托盘和简单配置窗口。
- 音频：NAudio 的 Core Audio 封装负责会话枚举和静音控制。第一版使用 500 毫秒定时扫描发现新会话；只有在性能测试证明需要时，才增加 Core Audio 会话创建通知。
- 配置：本地 JSON。
- 日志：本地文本日志，默认只记录错误和状态变化。
- 发布：自包含单文件或框架依赖发布，后续再增加代码签名。
- 权限：默认以普通用户权限运行，提供显式管理员模式；管理员模式需要单独处理 UAC、单实例和配置文件边界。

选择 WinForms 是因为托盘、设置窗口和后台循环已经足够，避免为第一版引入复杂的 UI 框架。
不使用 WebView 或 Electron，以满足低内存和快速启动目标。

## 5. 组件划分

### 5.1 AppRuleStore

负责保存和加载应用规则。

规则模型：

```json
{
  "id": "wechat",
  "displayName": "微信",
  "executablePaths": [
    "C:\\Program Files\\Tencent\\WeChat\\WeChat.exe"
  ],
  "enabled": true
}
```

匹配规则：

- 优先使用规范化后的完整进程路径，避免只按窗口标题匹配。
- 使用 `QueryFullProcessImageName` 读取进程路径；路径不可读取时，才回退到进程文件名，并记录警告。
- 多个 PID 只要路径匹配，就属于同一个应用规则。
- 辅助进程只能通过用户手动添加的路径纳入同一规则；第一版不自动推断父子进程关系，避免误静音共享组件。
- 首次运行时扫描当前运行且存在音频会话的进程，向用户展示微信、QQ、钉钉等候选应用。
- 自动检测到常见聊天软件时，可以创建已启用规则，但首次运行界面必须显示检测结果，用户可以直接取消。
- 用户可以从候选进程列表选择应用，也可以手动选择 EXE 路径添加规则。
- 如果没有任何可用规则，程序不得静默伪装成已开启免打扰；必须提示用户先选择至少一个应用。

### 5.2 AudioSessionScanner

负责枚举活动播放设备上的音频会话，输出统一的会话快照：

- 进程 ID。
- 进程路径。
- 会话标识。
- 会话实例标识。
- 当前静音状态。
- 会话状态。
- 枚举所有数据流为播放、状态为活动的音频端点，而不只枚举默认播放设备，避免蓝牙耳机、虚拟声卡或切换设备后漏掉会话。
- 同一个会话快照在多个扫描结果中重复出现时，按会话标识和会话实例标识去重。
- 免打扰开启时，扫描频率默认为 500 毫秒；免打扰关闭时停止后台音频扫描。
- 扫描使用单线程串行执行，避免多个扫描任务并发修改状态。
- 设备枚举器在整个进程生命周期内复用，每个扫描周期只刷新端点与会话快照，避免频繁创建 COM 对象。

### 5.3 AudioSessionController

负责：

- 对匹配会话设置静音。
- 记录本工具修改过的会话。
- 按记录恢复原静音状态。
- 处理已经结束或消失的会话。

不得使用“把音量调成 0”代替静音。

### 5.4 DndStateMachine

负责全局免打扰状态：

- Off：停止自动静音，恢复本工具管理的会话。
- On：扫描并静音当前匹配会话，同时持续扫描新会话。
- Recovering：启动时处理上次异常退出遗留的状态记录。

状态切换必须幂等。重复点击开启或关闭不能重复改写状态。

### 5.5 TrayApplication

提供：

- 主窗口中的大号免打扰开关。
- 完成首次配置后，默认打开主界面后立即开启免打扰；设置中可关闭这个行为。
- 托盘图标和右键菜单。
- 应用规则列表。
- “添加当前应用”入口。
- 启动时可选最小化到托盘。
- 关闭主窗口默认只隐藏到托盘，不停止免打扰。
- 只有用户从托盘选择“退出”时，才恢复本工具修改过的会话并结束程序。

### 5.6 PrivilegeManager

负责普通模式和可选管理员模式之间的切换：

- 默认使用 `asInvoker` 启动，不请求管理员权限。
- 用户点击管理员模式按钮后不在原地修改权限，而是通过 UAC 重新启动一个管理员实例。
- 重新启动时使用内部参数区分普通实例和管理员实例，避免提权循环。
- 使用单实例 Mutex，确保同一时间只有一个 ChatDND 在管理音频会话。
- 提权前普通实例进入暂停状态，保存待移交状态并释放单实例锁；管理员实例取得锁后通知普通实例退出。
- 如果 UAC 被取消或管理员实例启动失败，普通实例重新取得锁并恢复暂停前的扫描状态。
- 管理员实例接管后，可以恢复普通实例已经记录且状态明确的免打扰开关；未知会话状态不操作。
- 默认不提供开机管理员自启。如果用户明确启用“开机后以管理员身份运行”，使用任务计划程序实现，并在设置页持续显示风险说明。
- 如果管理员凭据属于另一个 Windows 账户，程序使用该账户自己的本地配置目录，并在风险提示中说明设置不会与普通用户配置共享。

## 6. 会话状态模型

本工具为每个被管理的会话保存：

```text
SessionKey
ProcessId
ProcessPath
OriginalMute
MutedByTool
LastSeenAt
```

`SessionKey` 由会话标识和会话实例标识组成；两者相同时才视为同一个可恢复的音频会话。

恢复规则：

- `MutedByTool=true` 且 `OriginalMute=false`：关闭免打扰时恢复为未静音。
- `MutedByTool=true` 且 `OriginalMute=true`：保持静音，不改变用户原始状态。
- 会话已消失：删除记录，不执行恢复。
- 会话在免打扰开启期间新建：先记录原始状态，再静音。

## 7. 运行流程

### 7.1 开启免打扰

1. 如果没有任何可用规则，提示用户先选择应用，不进入假的开启状态。
2. 校验当前状态，防止重复执行。
3. 枚举所有活动播放设备上的音频会话。
4. 按规则筛选匹配会话。
5. 记录每个会话的原始静音状态。
6. 对所有匹配会话执行静音。
7. 启动 500 毫秒定时扫描。
8. 更新托盘状态。

### 7.2 运行期间

每次扫描都会：

1. 重新枚举当前会话。
2. 忽略已经由本工具静音且状态未变的会话。
3. 对新出现的匹配会话执行静音。
4. 检查音频设备是否变化，变化后重新枚举。
5. 清理已经不存在的会话记录。

### 7.3 关闭免打扰

1. 停止定时扫描。
2. 枚举当前仍存在的受管会话。
3. 按原始状态执行恢复。
4. 清空运行时会话记录和恢复日志。
5. 更新托盘状态。

### 7.4 正常退出

关闭主窗口只隐藏到托盘，免打扰继续运行。用户从托盘选择“退出”时，退出前执行关闭免打扰流程，避免聊天应用被永久静音。持久化配置保留，但免打扰状态不跨正常退出保持。

### 7.5 异常退出恢复

程序在每次修改会话状态时写入本地恢复日志。下次启动时：

1. 读取恢复日志。
2. 尝试找到仍存在的会话。
3. 将本工具静音且原本未静音的会话恢复。
4. 删除已经无效的记录。
5. 显示一次恢复结果，不自动重新开启免打扰。

第一版不能保证进程崩溃后立即恢复，但需要在下次启动时完成恢复。

## 8. 错误处理

- 会话在枚举和修改之间结束：忽略该会话，不视为致命错误。
- 进程路径读取失败：使用 `QueryFullProcessImageName` 失败后，回退到文件名并记录警告。
- 受保护或权限不足的会话：跳过，记录日志，不导致整个免打扰流程失败。
- 未由用户显式添加到规则的共享辅助进程：跳过并记录日志，避免误静音其他软件。
- 音频设备切换、休眠恢复、默认设备变化：重新扫描并重新应用规则。
- Core Audio 调用失败：记录错误，下一轮扫描重试。
- 配置文件损坏：使用默认配置并保留损坏文件备份。
- 恢复日志损坏：以安全为先，不批量修改未知会话，提示用户检查。

## 9. 安全与隐私

- 程序不联网。
- 不读取消息内容、剪贴板、键盘输入或窗口文本。
- 不修改目标应用的配置、注册表、联系人或账号状态。
- 不注入目标进程，不安装驱动。
- 默认以当前用户权限运行。
- 管理员模式必须由用户显式确认，并显示中文风险说明。
- 管理员实例禁止加载任意脚本或插件，只加载程序自身代码、经过校验的配置文件和安全的内置规则。
- 管理员实例仍然只调用 Windows Core Audio 音频会话接口，不因为提权而扩展应用内部操作。
- 管理员模式自动启动只能通过用户明确开启的任务计划程序实现，不能在安装时默认创建。
- 发布前对可执行文件和安装包进行代码签名，减少被替换、篡改和安全软件误报的风险。
- 配置和日志只保存在用户本地目录。
- 恢复日志只保存进程路径、会话标识、静音状态和时间，不保存任何消息内容。

## 10. MVP 范围

第一版必须包含：

- 托盘程序和主开关。
- 完成首次配置后，打开程序默认进入免打扰，并允许用户在设置中关闭自动开启。
- 微信、QQ、钉钉的可编辑应用规则。
- 首次运行自动发现候选应用；没有规则时明确提示，不进入假的开启状态。
- 多 PID、多会话匹配。
- 覆盖所有活动播放设备，而不仅是默认播放设备。
- 新会话自动静音。
- 原静音状态恢复。
- 音频设备变化重扫。
- 正常退出恢复和启动恢复日志。
- 本地配置和错误日志。
- 全部用户界面和错误提示使用简体中文。
- 记录空闲和长期运行的内存数据，并完成至少一次内存优化。
- 提供显式的管理员模式入口、中文风险确认窗口和 UAC 取消后的安全回退。

第一版暂不包含：

- 消息提示音和语音通话的智能区分。
- 基于日程的自动免打扰。
- 云同步。
- 自动更新。
- 复杂主题和动画。

## 11. 验收标准

1. 开启免打扰后，已打开的微信、QQ、钉钉音频会话被静音。
2. 开启免打扰后新启动的第二个或第三个实例会在 1 秒内被静音。
3. 未选中的应用音量、静音状态和播放状态不受影响。
4. 关闭免打扰后，原本未静音的受管会话恢复有声。
5. 原本已经静音的会话关闭免打扰后仍保持静音。
6. 正常退出程序后，受管会话恢复。
7. 强制结束程序后，再次启动程序可以恢复遗留状态。
8. 切换默认音频设备或从休眠恢复后，规则继续生效。
9. 非管理员账户可以完成上述流程。
10. 主窗口、托盘菜单、设置页、提示框和错误提示均为简体中文；必要英文术语带中文说明。
11. 程序运行期间不写目标应用目录、注册表、联系人、通讯录或账号设置。
12. 空闲运行 10 分钟后，工作集以低于 80 MB 为优化目标；若超过，需要提供测量数据和优化结论。
13. 首次启动默认不弹出 UAC；只有用户主动选择管理员模式时才出现权限确认。
14. 用户取消管理员模式或 UAC 后，程序不会崩溃、不会遗留管理员实例，也不会改变已有免打扰状态。
15. 管理员模式下仍然只修改音频会话，不修改目标应用联系人、配置、账号或内部免打扰设置。
16. 管理员模式退出时，受管会话能够恢复；即使异常退出，也不会因为权限提升而跳过恢复日志流程。
17. 首次运行先完成应用选择；之后打开程序默认进入免打扰，设置中关闭自动开启后只打开主界面。
18. 首次运行能够显示检测到的候选应用；没有规则时会明确提示用户先选择应用。
19. 音频输出切换到头戴式耳机、蓝牙设备或虚拟声卡后，已打开的多开实例仍能被静音。
20. 对于无法确认归属的共享辅助进程，程序跳过而不是误静音其他应用。

## 12. 验证方法

### 自动测试

- 规则匹配：不同大小写路径、重复路径、缺失路径。
- 状态恢复：原始静音、原始未静音、会话消失、重复关闭。
- 状态机：重复开启、重复关闭、异常顺序关闭。
- 恢复日志：正常退出、崩溃模拟、日志损坏。
- 内存：空闲运行、持续开关免打扰、24 小时长时间运行后的工作集变化。
- 隔离：检查程序不会写入目标应用目录、注册表或配置文件。
- 权限：普通模式运行、主动提权、取消 UAC、管理员模式退出和任务计划程序自启。
- 路径匹配：完整路径、大小写差异、显式添加的辅助进程路径、无法读取路径。
- 启动行为：默认自动开启、设置关闭自动开启、无规则启动。

### 集成测试

- 使用两个以上真实聊天软件实例验证多开。
- 使用一个未选中的播放器验证隔离性。
- 切换默认播放设备、断开蓝牙耳机或启用虚拟声卡，并测试重新绑定。
- 强制结束 ChatDND 后重新启动，验证恢复。
- 在普通权限不足的会话上测试管理员模式，并在取消 UAC 后验证普通模式仍可正常工作。

因为音频会话依赖真实 Windows 桌面环境，集成测试需要在本机手工执行。

## 13. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 应用尚未创建音频会话 | 第一声提示音可能漏过 | 使用 500 毫秒扫描；明确第一声无法绝对保证，后续再评估会话创建通知 |
| 聊天软件使用辅助进程 | 部分声音未静音 | 允许用户显式添加辅助进程路径，第一版不自动推断 |
| 受保护或提权会话 | 无法修改 | 跳过并记录日志，提供“以管理员运行”的诊断选项 |
| 程序异常崩溃 | 会话可能暂时保持静音 | 恢复日志加下次启动恢复 |
| 应用更新改变进程结构 | 规则失效 | 允许用户重新绑定进程路径并显示匹配状态 |
| 用户期望只静音消息提示音 | 语音和视频也被静音 | 在 UI 中明确说明第一版为全部音频静音 |
| 低内存目标与 .NET 运行时基线冲突 | 空闲工作集可能高于预期 | 禁用重型 UI，及时释放 COM 对象，发布前测量并优化 |
| 只枚举默认播放设备 | 切换耳机或蓝牙后漏静音 | 枚举所有活动播放设备并按会话去重 |
| 共享辅助进程归属不明 | 可能误静音其他软件 | 第一版只处理显式添加的路径，未添加的共享进程跳过并记录 |
| 首次运行没有规则 | 用户误以为免打扰已生效 | 首次运行自动发现候选应用，无规则时明确阻止假的开启状态 |
| 扫描频率与低内存目标冲突 | CPU 或内存占用升高 | 只在免打扰开启时扫描，单线程串行，使用后释放 COM 对象 |
| 管理员模式扩大安全影响范围 | 程序漏洞或文件被替换可能影响系统 | 默认不提权，显式确认风险，限制代码路径，尽快加入代码签名 |
| UAC 取消或重复提权 | 可能出现双实例或状态冲突 | 单实例 Mutex，普通实例暂停并移交，取消 UAC 后恢复暂停状态 |
| 管理员模式自动启动绕过 UAC | 降低系统安全边界 | 默认关闭，必须由用户单独开启任务计划程序并持续显示风险说明 |
| 管理员账户与普通用户账户不同 | 配置和日志可能不一致 | 检测账户差异，提示并隔离配置，不静默覆盖 |

## 14. 评审结论

方案 A 已确定为第一版方向。用户已同意总体规格，并补充了低内存、应用内部隔离、中文界面和可选管理员模式四条硬约束。设计自审后已修正默认设备覆盖、首次运行空规则、关闭窗口语义、进程路径读取和扫描策略问题。下一步等待用户复查本规格，再编写实施计划。
